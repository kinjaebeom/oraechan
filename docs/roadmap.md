# 단계별 로드맵

## Phase 0 — 초기 환경

- GitHub 원격 연결과 기존 파일 확인.
- Next.js Pages Router, React, TypeScript, Tailwind, pnpm, ESLint 구성.
- 서비스명과 슬로건만 있는 최소 시작 페이지.
- README, 요구사항, 아키텍처, 디자인 시스템, 로드맵 작성.
- 파송 원본을 디자인 참고자료로 보관.
- 설치·lint·타입 검사·빌드·개발 서버 검증.

## Phase 1 — 감정·메시지 기반 맞춤 추천

`feat/emotion-hymn-recommendation`에 구현과 검증을 완료했습니다. 감정 또는 메시지를 선택하면 등록된 찬송가 5곡과 추천 이유가 표시됩니다. 추천곡·대표곡·카테고리 목록은 공용 YouTube 플레이어로 연결되며, 영상은 처음부터 시간 제한 없이 재생됩니다. 브랜치는 원격에 올라가 있으며 PR 생성과 검토가 남아 있습니다.

## Phase 2 — i18next + Locize 다국어 지원

예정 브랜치는 `feat/i18next-locize`입니다. 인프랩 프론트엔드의 i18n 학습 목표를 실제 서비스에 적용합니다.

- Pages Router에 i18next와 react-i18next를 구성하고 Locize에 번역 관리를 연결합니다. 한국어와 영어로 시작하고, 일본어 등은 언어 설정과 리소스를 추가해 확장할 수 있게 설계합니다.
- 언어별 URL과 언어 전환 UI를 제공합니다. 서버 렌더와 클라이언트 첫 렌더에는 같은 언어와 번역 리소스를 사용합니다. 번역이 누락되면 한국어 원문을 표시하고, 언어 전환·직접 접근·새로고침에서 hydration 오류가 없는지 확인합니다.
- 메뉴, 감정 카드, 메시지 버튼, 추천 태그·이유·상태와 직접 작성한 서비스 소개를 번역합니다. 가사 번역은 범위에서 제외합니다. 한국어 원문에서 AI 번역 초안을 만들고 검수 후 반영하는 절차를 검토합니다.
- [Locize Free 요금제](https://www.locize.com/pricing)는 지원 언어 2개와 저장 단어 총 2,000개를 제공합니다. **1,800단어 이상 경고, 신규 등록 후 사용량이 1,950단어 이상이면 등록 제한**을 오래찬 기준으로 둡니다. 기존 번역도 단어 수가 늘어나는 수정이나 일괄 가져오기는 같은 기준을 적용합니다.
- Locize 계정에서 실사용량을 확인할 수 있는 수단을 검증합니다. 쓰기 요청은 서버에서 최신 실사용량과 추가분을 합산해 검증하고, 동시 등록에도 한도를 적용합니다. 실사용량을 확인할 수 없으면 자동 등록을 보류하고 관리자 확인을 거칩니다. 유료 플랜이나 유료 API는 사용자 승인 후에만 사용합니다.

## Phase 3 — 찬송가 직접 검색 및 영상 감상

예정 브랜치는 `feat/hymn-search`입니다. 초기 검색 범위는 `src/data/hymns.ts`에 등록된 찬송가입니다.

- 제목의 일부로 검색할 수 있게 하고, 공백과 대소문자를 정규화한 뒤 입력을 디바운싱합니다. 검색 결과 없음, 진행 중, 오류 상태를 표시하고, 모바일 레이아웃과 키보드로 결과를 고르는 흐름을 검증합니다. 제목 부분 일치와 정규화는 단위 테스트로 확인합니다.
- 곡을 고를 때 기존 곡 ID로 `/api/hymn-video`를 호출합니다. 밴드·워십팀 우선순위와 기존 캐시를 활용하고, 공용 YouTube 플레이어에서 영상을 처음부터 시간 제한 없이 재생합니다.
- 등록되지 않은 찬송가·CCM의 YouTube 검색은 후속 확장으로 검토합니다. 공개 전에 서버에서 입력 길이와 형식을 검증하고, 서버 인스턴스 간 공통 호출 제한, 검색 결과 캐시, 프로젝트 단위 할당량 보호를 설계합니다.

## Phase 4 — 테스트·성능 최적화·배포

- 추천·검색·언어 전환·영상 감상 흐름의 경계 사례와 접근성을 점검합니다. 필요에 따라 Storybook, Vitest, React Testing Library, 자동 접근성 검사, GitHub Actions, Lighthouse를 적용하고 실제 썸네일 도입 시 이미지 최적화를 검토합니다.
- Vercel 배포 전에 콘텐츠·영상·모바일·오류 처리와 외부 서비스 사용량을 점검합니다.

## 후속 확장

- 곡별 상세 URL과 묵상 콘텐츠, 필터, 즐겨찾기·공유, 사용자 피드백, 곡 확충과 외부 추천 폼을 검토합니다. 동기화나 공개 댓글은 별도 저장 서비스의 필요성을 판단한 뒤 진행합니다.
- 카드/리스트 기능 플래그와 이벤트 POC를 검토합니다. SSR, pnpm Workspaces/Turborepo, Module Federation은 각 기술을 적용할 구체적인 필요가 생겼을 때 검토합니다.
- 수익화는 장기 검토 사항입니다.

## 작업 순서와 Git 규칙

맞춤 추천 변경 정리 → 다국어 지원 → 찬송가 직접 검색 → 테스트·성능 최적화·배포 순으로 진행합니다. 각 기능은 별도 브랜치와 PR에서 다루고, 변경 후 관련 테스트와 `pnpm lint`, `pnpm typecheck`, `pnpm build`를 실행합니다. `main` 병합은 사용자 승인 후 진행합니다.
